01Why design patterns — shared vocabulary for recurring problems★ start here▶

Scenario: in a review you say "let's inject a strategy here and wrap the client in a decorator with a circuit breaker" — and the whole team instantly knows the shape of the solution. That's the real value of patterns: names for solutions that recur, so you design and communicate faster and recognize structures already proven in the wild.

What

Design patterns are named, reusable solutions to problems that keep recurring in software design — a shared vocabulary (from the 1994 "Gang of Four" book and beyond), not copy-paste code.

Why

They compress communication ("it's an adapter"), encode hard-won tradeoffs, and help you recognize structures you already see in frameworks — so you don't reinvent (or misuse) them.

How

Learn the problem each solves, not just its diagram. Reach for one when you hit its problem — never apply a pattern for its own sake (topic 28).

Three families (plus modern architectural ones)
   CREATIONAL   how objects are CREATED     Factory, Builder, Singleton, Pool…
   STRUCTURAL   how objects are COMPOSED    Adapter, Decorator, Facade, Proxy…
   BEHAVIORAL   how objects INTERACT        Strategy, Observer, Command, State…
   MODERN       app/infra architecture      Repository, Pub/Sub, Circuit Breaker
   a pattern = (recurring problem) → (proven solution) → (its tradeoffs)
🧠
Patterns are chess openings: "Sicilian Defense" names a whole plan both players recognize. You don't play an opening to show off — you play it because the position calls for it. Same with patterns: the situation calls for a Strategy, so you name and use one.
📚
Framework docs already speak patterns: React "render props," Spring "template," Node "streams/observer," Express "middleware chain." Learning patterns is learning to read the frameworks you already depend on.
Same idea, one shared word
// without vocabulary — a long explanation:
"make an object that stands in for the real client, and around it wrap
 something that adds retry, and something that trips after N failures…"

// with vocabulary — one sentence a reviewer parses instantly:
const client = new CircuitBreaker(new RetryDecorator(new HttpClient(), 3))
//               ^ pattern 27          ^ pattern 09 (decorator)   ^ the real thing
// the NAMES carry the design. that's what patterns buy you.
🧒
In plain wordsDesign patterns are just named recipes for problems programmers keep bumping into. Once everyone knows the recipe names, you can say "let's use the such-and-such recipe" and skip the long explanation. The point isn't to use fancy recipes everywhere — it's to recognize when you're facing a problem someone already solved well, and reuse that solution.
🌍
In the wildThe GoF book Design Patterns (1994) named 23 of these; frameworks are built from them — React (composition, HOCs/decorators, render props), Spring (template method, proxy, factory), Node streams (observer/iterator), Express/Rack (chain of responsibility). Cloud resilience libraries (Hystrix, Polly, resilience4j) ship circuit breakers and retries as named building blocks.

✅ Do

  • Learn the problem each pattern solves and its tradeoffs
  • Use patterns to communicate design intent quickly
  • Recognize patterns already in your frameworks and lean on them

❌ Don't

  • Apply a pattern because it's clever — apply it because you have its problem
  • Treat the GoF diagrams as mandatory boilerplate to reproduce verbatim
Gotcha: patterns are a vocabulary, not a checklist. The classic failure (topic 28) is "pattern fever" — forcing Singletons, Factories, and Visitors onto code that a plain function or a language feature would handle better. Modern languages absorbed several GoF patterns as built-ins (iterators, first-class functions replacing Strategy/Command, Optional replacing Null Object). Know them to recognize and communicate — reach for them only when the recurring problem actually shows up.
02Factory Method — decide the concrete type in one place★ core▶

Scenario: your code needs a Logger, but which one — console in dev, JSON-to-stdout in prod, a no-op in tests — depends on config. Scattering new JsonLogger() everywhere hard-codes the choice. A factory method centralizes "which concrete class to build" behind a single call: Logger.create(env).

What

Factory Method: a method whose job is to create and return an object, deciding the concrete type internally. Callers ask for the abstraction and get back a ready-made instance.

Why

It puts the "which class + how to build it" decision in one place, so callers stay decoupled from concrete constructors and construction logic isn't duplicated.

How

Replace scattered new X() with a factory function/method that returns the interface type and picks the implementation (by config, input, or platform).

One place decides the concrete type
   callers:  const log = makeLogger(env)     ← ask for a Logger
                          │
                   ┌──────┴───────┐  factory decides:
              env==='prod'?   env==='test'?
                   │               │
              JsonLogger       NoopLogger      (else) ConsoleLogger
   change the selection rule ONCE, in the factory — not at every call site
🧠
React.createElement is a factory: JSX compiles to React.createElement(type, props), which builds the right element object for you — you never new a fiber. document.createElement('div') is the DOM's factory doing the same.
🏭
Config-driven construction: logging.getLogger() (Python), a DriverManager.getConnection(url) that returns the right JDBC driver, and DocumentBuilderFactory all hide "which concrete class + how to build it" behind one call.
A factory picks the implementation by config
interface Logger { info(msg: string): void; error(msg: string): void }
class ConsoleLogger implements Logger { /* ... */ }
class JsonLogger    implements Logger { /* ... */ }
class NoopLogger    implements Logger { info(){} error(){} }

function makeLogger(env: string): Logger {         // the factory method
  if (env === 'production') return new JsonLogger()
  if (env === 'test')       return new NoopLogger()
  return new ConsoleLogger()
}
// callers: const log = makeLogger(process.env.NODE_ENV)  — no `new` at call sites
🧒
In plain wordsInstead of every part of your code knowing how to build the exact thing it needs, they all ask one helper: "give me a logger." The helper figures out which kind to make based on the situation and hands it over. If you later change how loggers are chosen, you fix the one helper — not a hundred places that each said "build a JSON logger."
🌍
In the wildReact.createElement / document.createElement, Python logging.getLogger, Java DocumentBuilderFactory / Calendar.getInstance() / DriverManager.getConnection, AWS SDK S3Client.builder().build(), and ORM createConnection(config). Any createX() / makeX() / getX() that hides which concrete class you get is a factory.

✅ Do

  • Centralize "which implementation + how to build it" in a factory
  • Return the interface type so callers stay decoupled
  • Use it when construction depends on config, input, or platform

❌ Don't

  • Wrap a single trivial new in a factory for no reason
  • Let the factory grow into a God object that builds unrelated things
Gotcha: in languages with first-class functions, a factory is often just a function — you rarely need the full GoF "creator subclass overrides factoryMethod()" hierarchy. And don't confuse Factory with Dependency Injection: a factory creates objects on demand (you call it when you need one); DI supplies already-created collaborators (you receive them). They compose — a DI container often uses factories internally — but reaching for a factory when you actually just want to inject a dependency adds a needless layer.
03Abstract Factory — families of related objects▶

Scenario: your app targets AWS and GCP. On AWS you need an S3 blob store, SQS queue, and CloudWatch metrics; on GCP, GCS, Pub/Sub, and Stackdriver. You must never mix an S3 store with a Pub/Sub queue. An abstract factory hands you a whole compatible family at once: cloud.blobStore(), cloud.queue(), cloud.metrics() — all AWS, or all GCP.

What

Abstract Factory: an interface for creating a family of related objects without specifying their concrete classes, so the whole set stays consistent.

Why

It guarantees the pieces you get work together (all AWS, or all GCP, or all "dark theme") and lets you swap the entire family by swapping one factory.

How

Define a factory interface with several create-methods; implement one factory per family; inject the chosen factory and build all pieces through it.

Pick the family once; every piece matches
   interface CloudFactory { blobStore()  queue()  metrics() }
        ┌───────────────────────┴───────────────────────┐
   AwsFactory                                        GcpFactory
     blobStore → S3        queue → SQS                blobStore → GCS
     metrics   → CloudWatch                           queue → PubSub, metrics → Stackdriver
   inject AwsFactory ⇒ you CAN'T accidentally get an S3 store with a PubSub queue
🧠
Cross-platform UI toolkits are the textbook case: a WidgetFactory that makes a matching Button, Checkbox, and Menu for macOS or Windows — so you never render a Windows button next to a macOS checkbox. Same shape as "all-AWS vs all-GCP."
🎨
Theme providers: a ThemeFactory yields a consistent set of colors, spacings, and components for "dark" or "light." One switch changes the entire coordinated family, not thirty individual choices.
A factory per cloud; the family stays consistent
interface CloudFactory {
  blobStore(): BlobStore
  queue(): Queue
  metrics(): Metrics
}
class AwsFactory implements CloudFactory {
  blobStore(){ return new S3Store() }
  queue(){ return new SqsQueue() }
  metrics(){ return new CloudWatch() }
}
class GcpFactory implements CloudFactory {
  blobStore(){ return new GcsStore() }
  queue(){ return new PubSubQueue() }
  metrics(){ return new Stackdriver() }
}
// wire once: const cloud: CloudFactory = onAws ? new AwsFactory() : new GcpFactory()
// everything built from `cloud` is guaranteed same-family
🧒
In plain wordsSometimes you need a matching set of things — like a whole outfit where the shoes, belt, and bag all go together. An abstract factory is the shop assistant who, once you pick "the summer collection," hands you pieces that all match. You can't accidentally end up with winter boots and a summer hat, because everything came from the same coordinated set.
🌍
In the wildCross-platform UI toolkits (Swing look-and-feels, Qt styles), cloud-provider abstraction layers, database provider families in ORMs/EF Core (DbProviderFactory), Java's DocumentBuilderFactory/TransformerFactory, and theming systems. Whenever swapping one setting must swap a coordinated group of implementations together, it's an abstract factory.

✅ Do

  • Use it when several objects must come from the same family
  • Swap the entire family by injecting a different factory
  • Keep the create-methods cohesive (one real family per factory)

❌ Don't

  • Reach for it when you only ever build one kind of object (that's Factory Method)
  • Add a factory family for variation that will never have a second member
Gotcha: Abstract Factory is one of the heaviest creational patterns — lots of interfaces and classes for the guarantee of family-consistency. If you have one product that varies, you want a plain Factory Method (topic 2), not this. And adding a new product to the family (say, secrets()) forces you to edit every factory implementation — so only pay for it when you genuinely have multiple, related products that must stay in lockstep across swappable families.
04Builder — assemble complex objects step by step★ very common▶

Scenario: constructing an HTTP request needs a URL, method, headers, query params, body, timeout, retries — most optional. A constructor with ten positional args (new Request(url, 'POST', null, null, headers, …)) is unreadable and error-prone. A builder assembles it fluently: request().url(u).header('Auth', t).timeout(5000).build().

What

Builder: separate the step-by-step construction of a complex object from its representation, usually via a fluent chain that ends in build() (which validates invariants).

Why

It kills the "telescoping constructor" (many overloads / long positional arg lists), makes optional fields readable, and validates the whole thing once at build() — so you never get a half-configured object.

How

A builder object accumulates settings via chainable methods (each returns this), then build() constructs and validates the final immutable object.

Fluent steps → one validated object
   request()                     ❌ vs telescoping constructor:
     .url('/orders')                new Request('/orders','POST',null,
     .method('POST')                            headers,null,5000,3,false…)
     .header('Auth', token)           which null is the body? good luck.
     .timeout(5000)
     .retries(3)
     .build()   ← validates here, returns an immutable Request
🧠
Query builders are builders: Knex/jOOQ/SQLAlchemy — db('users').where('active', true).orderBy('name').limit(10) — accumulate a complex SQL statement step by step, then execute. Each call returns the builder so you can keep chaining.
🌐
HTTP clients ship builders: OkHttp's Request.Builder, Java's HttpRequest.newBuilder(), and axios/fetch config objects all assemble a request from many optional parts and validate at the end.
A fluent request builder that validates at build()
class RequestBuilder {
  private req: any = { method: 'GET', headers: {}, timeout: 30000 }
  url(u: string){ this.req.url = u; return this }          // each step returns this
  method(m: string){ this.req.method = m; return this }
  header(k: string, v: string){ this.req.headers[k] = v; return this }
  timeout(ms: number){ this.req.timeout = ms; return this }
  build(): Request {
    if (!this.req.url) throw new Error('url is required')   // invariant checked ONCE
    return Object.freeze(this.req)                          // immutable result
  }
}
const r = new RequestBuilder().url('/orders').method('POST').header('Auth', tok).build()
🧒
In plain wordsWhen a thing has lots of optional parts, don't cram them all into one giant "make it" call where you can't tell which blank is which. Instead, add the parts one at a time with clear names — "set the URL," "add this header," "set a 5-second timeout" — and then say "build it." At the end it checks everything's sensible and hands you the finished, locked object.
🌍
In the wildOkHttp Request.Builder, Java HttpRequest/StringBuilder/Stream.Builder, query builders (Knex, jOOQ, SQLAlchemy, ActiveRecord's chainable scopes), Kubernetes manifest builders, protobuf message builders, Flutter widget trees, and "test data builders" (aUser().withEmail(...).build()) that keep test setup readable. Lombok's @Builder generates them automatically.

✅ Do

  • Use it for objects with many optional/complex parts
  • Validate all invariants once in build() and return something immutable
  • Use builders to make test setup readable

❌ Don't

  • Build a builder for a 2-field object — a constructor or object literal is clearer
  • Let the builder return a usable object before build() validates it
Gotcha: languages with named/optional/keyword arguments (Python, Kotlin, Swift, TS object params) already solve the "telescoping constructor" problem — Request(url, method='POST', timeout=5000) is as readable as a builder with less ceremony. Reach for a full Builder when you need staged construction, validation at the end, an immutable result, or a fluent DSL (like a query builder). For "just a lot of optional fields," a config object is often enough.
05Singleton — one instance, and why it's often a trap⚠ use sparingly▶

Scenario: you want exactly one database connection pool for the whole app, so you make it a global Singleton. Convenient — until tests can't swap it, two modules fight over its state, and it becomes hidden global coupling. Singleton is the most overused and criticized pattern; know it, and prefer DI (topic 18 in OOP) for most cases.

What

Singleton: ensure a class has exactly one instance and provide a global access point to it.

Why

Some resources are genuinely single (a process-wide connection pool, a config registry, a metrics client). But the "global access point" part causes hidden coupling and testing pain.

How

Prefer injecting a single instance created at your composition root over a global getInstance(). If you must use a true Singleton, keep it stateless-ish and behind an interface.

Singleton vs "one instance, injected"
  ❌ classic Singleton (global):        ✅ single instance via DI:
     Db.getInstance().query(...)          const db = new Pool(url)   // once, at root
        │  reachable from ANYWHERE         new OrderService(db)      // injected
        │  hidden dependency, hard to      new UserService(db)       // shared, explicit
        ▼  mock in tests, shared mutable   tests: new OrderService(fakeDb)
     global state = spooky coupling      one instance, but dependencies are visible
🧠
A Singleton is a global variable in a nicer suit. The "one instance" part is often fine; the "reachable from anywhere via getInstance()" part is the global-state problem that makes code hard to test and reason about — which is why DI is usually preferred.
🧪
The test tells the truth: if you can't replace it with a fake in a unit test without global hacks, it's too global. Injecting "the one pool" gives you singleness and testability — the best of both.
The trap vs the preferred approach
// ❌ classic Singleton — global access point, hard to test
class Db {
  private static instance: Db
  static getInstance(){ return Db.instance ??= new Db() }
}
Db.getInstance().query('...')   // called from anywhere; hidden global dependency

// ✅ create ONE instance at the composition root, inject it (topic: DI)
const pool = new Pool(process.env.DATABASE_URL)   // exactly one, made once
const orders = new OrderService(pool)             // dependency is explicit + swappable
// tests: new OrderService(fakePool)              // trivial — no global to stub
🧒
In plain wordsSometimes you truly want only one of something (one shared pool of database connections). The tricky part isn't making one — it's letting the whole program secretly grab it from anywhere, which makes things tangled and hard to test. Better: make the one thing at startup and hand it to whoever needs it. You still have exactly one; you just didn't make it a global that everyone reaches into.
🌍
In the wildLegitimate-ish singles: a process-wide connection pool, logger, config, or metrics client. But Java's Runtime.getRuntime() and many framework globals are cited as cautionary tales; modern DI containers (Spring, .NET, NestJS) provide "singleton scope" that gives you one instance with injection and testability. "Singleton = global state" is a well-known criticism — most style guides say prefer DI.

✅ Do

  • Prefer a single instance created at the root and injected
  • Use a DI container's singleton scope if you need one instance
  • Keep any true Singleton behind an interface so tests can substitute it

❌ Don't

  • Sprinkle getInstance() calls through business logic (hidden global coupling)
  • Store mutable request/user state on a Singleton (thread-safety + test hell)
Gotcha: Singletons hide dependencies and hold global mutable state, which is the root of subtle test flakiness (tests leak state into each other) and concurrency bugs. There's also a lazy-init thread-safety trap: naïve getInstance() can build two instances under a race. If you take one lesson from this card: the value you usually want is "exactly one instance," and you get that far more safely by constructing it once and injecting it than by making it globally reachable. Reserve true Singletons for genuinely process-global, stateless services.
06Prototype — create by cloning an existing object▶

Scenario: you have a fully-configured "default" object — a game enemy with 40 tuned fields, or a base API-request template with auth + retries set — and you need many near-identical copies with small tweaks. Rebuilding each from scratch is wasteful and error-prone. The Prototype pattern clones a preconfigured instance and adjusts the differences.

What

Prototype: create new objects by copying an existing "prototype" instance rather than constructing from scratch, then tweak what differs.

Why

When construction is expensive or configuration is elaborate, cloning a known-good instance is faster and avoids re-specifying dozens of fields correctly each time.

How

Give objects a clone() (or use structuredClone/Object.create), keep a registry of prototypes, and clone-then-modify to produce variants.

Clone a known-good template, tweak the diff
   prototype:  baseRequest { auth, retries:3, timeout:5s, headers{…} }
                     │ clone()
                     ▼
   variant A = clone(baseRequest); A.url = '/orders'
   variant B = clone(baseRequest); B.url = '/users'; B.timeout = 1s
   40 tuned fields copied for free; you only set what's DIFFERENT
🧠
JavaScript IS prototype-based: objects inherit from other objects via the prototype chain, and Object.create(proto) makes a new object backed by an existing one. Prototype is baked into the language, not bolted on.
🧬
"Duplicate this and change a couple of things": copying a Figma component, "Save As" on a document, or git branch off a known-good commit — start from a configured baseline instead of a blank page.
Clone a configured prototype, then tweak
const baseRequest = {                       // a fully-configured prototype
  headers: { Authorization: token }, retries: 3, timeout: 5000, method: 'GET',
}
// structuredClone gives a deep copy — the base is untouched
const getOrders = { ...structuredClone(baseRequest), url: '/orders' }
const getUser   = { ...structuredClone(baseRequest), url: '/users', timeout: 1000 }
// only the DIFFERENCES are specified; auth/retries/etc. come from the prototype

// classic OO form: objects expose clone()
class Enemy { clone(): Enemy { return structuredClone(this) } }
🧒
In plain wordsIf you already have one thing set up just right and you need lots of almost-identical ones, don't rebuild each from nothing — photocopy the good one and change the few bits that differ. Like keeping a filled-in form as a template and copying it each time instead of writing every field again. Faster, and you won't forget a setting.
🌍
In the wildJavaScript's prototypal inheritance and Object.create/structuredClone, Java's Cloneable/clone(), C#'s MemberwiseClone/ICloneable, prototype registries in game engines (spawn enemies from a template), deep-copying config templates, and copy-on-write data structures. Kubernetes/IaC "copy this manifest and change the name" is the same instinct.

✅ Do

  • Clone when construction is expensive or configuration is elaborate
  • Keep a registry of prototype instances to copy from
  • Be explicit about deep vs shallow copy

❌ Don't

  • Clone when a simple constructor call is cheaper and clearer
  • Shallow-copy an object with nested mutable state (aliasing bugs)
Gotcha: the shallow vs deep copy trap is the whole ballgame. A shallow clone copies top-level fields but shares nested objects/arrays by reference — so mutating copy.headers also mutates the prototype's headers, corrupting every future clone. Use structuredClone/deep copy for anything with nested mutable state, and remember that clones skip the constructor, so any invariant checks or side effects in your constructor won't run — validate cloned objects if that matters.
07Object Pool — reuse expensive objects▶

Scenario: opening a database connection takes 50–100ms (TCP + TLS + auth). If every query opened a fresh one, your API would crawl and the DB would drown in connection churn. An object pool keeps a set of ready connections and lends them out — the single most important reason your app can serve thousands of requests per second.

What

Object Pool: keep a set of reusable, expensive-to-create objects (connections, threads, buffers) and lend them to clients, who return them instead of destroying them.

Why

It amortizes expensive setup (TCP/TLS handshakes, thread creation) across many uses and caps resource usage (max connections) so you don't exhaust the DB or OS.

How

A pool tracks idle + in-use objects; acquire() hands out (or creates/blocks up to a max), release() returns it for reuse. Health-check on return.

Borrow → use → return, capped at a max
   ┌──── Connection Pool (max 20) ────┐
   │ idle: [c1 c2 c3]   in-use: [c4…] │
   └──────────────────────────────────┘
   acquire() ─► hands out c1 (or creates if under max, or WAITS if maxed)
   ...query...
   release(c1) ─► c1 goes back to idle (health-checked), ready for the next caller
   50ms handshake paid ONCE per connection, not once per query
🧠
Connection pools are why servers scale: HikariCP, pgbouncer, and every ORM's pool keep warm DB connections. Without pooling, connection setup cost and the DB's connection limit would cap you at a fraction of your throughput.
🧵
Thread pools are the same idea: creating an OS thread per task is expensive, so executors keep a fixed pool of worker threads and feed them a task queue — reuse over re-create, with a hard cap.
Acquire / release with a max size
class ConnectionPool {
  private idle: Conn[] = []
  private inUse = 0
  constructor(private max: number, private make: () => Conn) {}
  async acquire(): Promise<Conn> {
    if (this.idle.length) return this.idle.pop()!          // reuse a warm one
    if (this.inUse < this.max) { this.inUse++; return this.make() }  // or create
    return this.waitForRelease()                          // or WAIT (backpressure)
  }
  release(c: Conn){ if (c.healthy()) this.idle.push(c); else this.inUse-- } // return, checked
}
// the 50ms TCP+TLS+auth handshake is amortized across thousands of queries
🧒
In plain wordsSome things are slow and pricey to set up (like a phone call that takes a while to connect). Instead of hanging up and redialing for every little thing, you keep a few lines already open and share them: grab a free line, use it, hand it back. That's how a website can handle tons of visitors — it isn't opening a brand-new database connection for every single click.
🌍
In the wildDatabase connection pools (HikariCP, pgbouncer, node-postgres Pool, ActiveRecord/SQLAlchemy pools), HTTP keep-alive connection pools (OkHttp, undici), thread pools/executors (Java ExecutorService, .NET ThreadPool), byte-buffer pools (Netty), and game-engine object pools for bullets/particles. It's foundational to the scaling story in the Distributed Systems playbook.

✅ Do

  • Pool genuinely expensive resources (connections, threads, big buffers)
  • Cap the pool size to protect the downstream resource; apply backpressure when maxed
  • Health-check objects on return and reset their state before reuse

❌ Don't

  • Pool cheap objects — modern allocators/GC make that a pessimization
  • Forget to release() (a leak that exhausts the pool and hangs the app)
Gotcha: the two classic bugs are leaks and dirty state. Forget to release() (e.g. on an error path without try/finally) and the pool drains until every request blocks forever waiting for a connection — a nasty production hang. And a returned object carries its old state: a DB connection left mid-transaction, a buffer with stale bytes. Always reset/health-check on return, always release in a finally, and size the pool deliberately — too small starves throughput, too large overwhelms the DB (topic: Distributed Systems). Don't pool trivially cheap objects; you'll add complexity and often lose to the GC.

08Adapter — make an incompatible interface fit★ core▶

Scenario: your app talks to a PaymentGateway interface (topic: abstraction), but Stripe's SDK has its own method names and shapes (stripe.charges.create({amount, source})). An adapter is the thin translation layer that makes Stripe's API look like your PaymentGateway — without changing either side.

What

Adapter: wrap an object with an incompatible interface in a class that translates calls to the interface your code expects. (a.k.a. Wrapper.)

Why

It lets you integrate third-party or legacy code that you can't change, and keeps vendor-specific shapes out of your business logic (one translation point).

How

Implement your target interface; inside, delegate to the adaptee, mapping arguments and return values (and errors) between the two vocabularies.

Translate their shape into yours
   your code ──► «PaymentGateway.charge(Money, token)»   (what you want)
                        │  implemented by
                 StripeAdapter
                        │  translates → stripe.charges.create({amount, source})
                        ▼
                 Stripe SDK (the adaptee — unchanged, incompatible shape)
🧠
A travel plug adapter is the literal metaphor: it doesn't change the wall socket or your device — it sits between them and makes the shapes fit. A code adapter changes neither the SDK nor your interface; it bridges their signatures.
🔌
ORMs adapt databases: a PostgresAdapter, MySQLAdapter, SQLiteAdapter each make a specific driver satisfy the ORM's uniform interface — so the ORM core speaks one language while the drivers differ.
Adapter: your interface, their SDK underneath
interface PaymentGateway { charge(amount: Money, token: string): Promise<Receipt> }

class StripeAdapter implements PaymentGateway {          // YOUR interface
  constructor(private stripe: Stripe) {}
  async charge(amount: Money, token: string): Promise<Receipt> {
    const res = await this.stripe.charges.create({        // THEIR shape
      amount: amount.cents, currency: amount.currency, source: token,
    })
    return { id: res.id, status: res.status }             // translate back to YOURS
  }
}
// business code depends only on PaymentGateway; Stripe's vocabulary stops here
🧒
In plain wordsTwo things that should work together speak different "languages." Rather than rewrite either one, you put a little translator in the middle that turns your requests into theirs and their answers back into yours. Like a travel adapter for a foreign plug — nothing about the wall or your charger changes, the adapter just makes them fit.
🌍
In the wildORM database adapters (ActiveRecord, SQLAlchemy dialects), logging facades (SLF4J adapting Logback/Log4j), java.io.InputStreamReader (bytes→chars), Rack/WSGI adapting web servers to apps, wrapping any third-party/legacy SDK behind your own interface, and React wrappers around non-React widgets. Any "*Adapter"/"*Wrapper" class translating one API to another is this.

✅ Do

  • Use adapters to keep third-party/vendor shapes at the edges
  • Translate arguments, return values, and errors into your vocabulary
  • Keep one adapter per external system you integrate

❌ Don't

  • Let the adapter leak the adaptee's types (that defeats it — a leaky abstraction)
  • Add an adapter when you actually control both sides and could just align them
Gotcha: Adapter vs its neighbors trips people up. Adapter changes an interface to a different one you already need (integration); Decorator (topic 9) keeps the same interface but adds behavior; Facade (topic 10) invents a simpler interface over a complex subsystem. If you're translating shapes, it's an Adapter. And beware the leaky adapter: if it returns the adaptee's raw error/response types, callers still couple to the vendor and the whole point is lost — map everything at the boundary.
09Decorator — add behavior by wrapping★ very common▶

Scenario: you have an HttpClient, and you want to add retries, then caching, then auth headers, then request logging — composably, so you can mix and match per environment. A decorator wraps the client in another object with the same interface that adds one behavior and delegates the rest. Stack them like layers.

What

Decorator: wrap an object in another object implementing the same interface, adding behavior before/after delegating. Decorators nest, so behaviors stack.

Why

It adds responsibilities at runtime without subclass explosion (the composition-over-inheritance win): retry + cache + log = three small wrappers, any combination.

How

Each decorator takes the wrapped object, implements the interface, does its extra bit, and calls through. Compose by nesting: log(cache(retry(client))).

Same interface, stacked layers
   request ─► LoggingClient ─► CachingClient ─► RetryClient ─► HttpClient
                 │ log            │ hit? return   │ try 3×        │ real fetch
                 ▼ delegate       ▼ else delegate  ▼ delegate      ▼
   every layer is an HttpClient; caller can't tell how many wrappers are stacked
   mix per env: prod = log(cache(retry(c)))   test = c   (no wrappers)
🧠
Express/Rack middleware IS the decorator pattern: each middleware wraps the next, adding auth, gzip, logging around the request — a stack you compose. Same for HTTP client interceptors (axios, OkHttp) that layer retry/auth/tracing.
☕
Java I/O streams are the canonical example: new BufferedReader(new InputStreamReader(new FileInputStream(f))) — each wrapper adds buffering / decoding while keeping the Reader/InputStream interface. Python's @decorator syntax wraps functions the same way.
Wrap to add retry, then caching — same interface
interface HttpClient { get(url: string): Promise<Response> }

class RetryClient implements HttpClient {                 // adds retries
  constructor(private inner: HttpClient, private times = 3) {}
  async get(url: string) {
    for (let i = 0; i < this.times; i++) {
      try { return await this.inner.get(url) } catch (e) { if (i === this.times-1) throw e }
    }
    throw new Error('unreachable')
  }
}
class CachingClient implements HttpClient {               // adds caching
  private cache = new Map<string, Response>()
  constructor(private inner: HttpClient) {}
  async get(url: string){ return this.cache.get(url) ?? this.set(url) }
  private async set(u: string){ const r = await this.inner.get(u); this.cache.set(u,r); return r }
}
// compose: const client = new CachingClient(new RetryClient(new RealHttpClient()))
🧒
In plain wordsTake something that works, and wrap it in a layer that adds one extra ability — like putting a phone in a waterproof case, then a grippy case, then a wallet case. Each layer still acts like "the phone," but adds a feature. In code you stack wrappers (retry, cache, logging) around a client and mix them however you like, without inventing a new class for every combination.
🌍
In the wildExpress/Koa/Rack middleware, HTTP interceptors (axios, OkHttp, gRPC), Java I/O streams (BufferedReader, GZIPInputStream), Python function @decorators, React Higher-Order Components and hooks that wrap behavior, Redux middleware, and resilience wrappers (retry/cache/circuit-breaker layered around a client — see topic 27). It's composition-over-inheritance made concrete.

✅ Do

  • Use decorators to add cross-cutting behavior (retry, cache, log, auth) composably
  • Keep each decorator to one responsibility and delegate the rest
  • Compose per environment (prod stacks wrappers; tests use the bare object)

❌ Don't

  • Change the interface in a decorator (that would make it an Adapter, not a Decorator)
  • Stack so many layers that debugging a call means peeling ten wrappers
Gotcha: deeply nested decorators make stack traces and debugging painful — a failing request may pass through eight wrappers, and it's hard to see which layer misbehaved or what order they run in (order matters: caching-outside-retry vs retry-outside-caching behave differently). Keep the stack shallow and its composition explicit in one place. Also note the naming clash: Python/TS @decorator syntax and Java annotations are related but not identical to the GoF object-wrapping Decorator — same spirit, different mechanism.
10Facade — one simple door over a complex subsystem▶

Scenario: placing an order really means: validate the cart, reserve inventory, charge payment, create a shipment, send a confirmation email, and emit analytics — six subsystems. Callers shouldn't orchestrate all that. A facade — checkout.placeOrder(cart, payment) — presents one simple method that coordinates the mess behind it.

What

Facade: a single, simplified interface in front of a complex subsystem, hiding its many moving parts behind one coherent entry point.

Why

It reduces the surface callers must understand, decouples them from subsystem details, and gives you one place to change the orchestration.

How

Create a class whose methods coordinate the subsystems for common use cases. Callers use the facade; the subsystems stay usable directly for advanced needs.

One method, many subsystems behind it
   caller ──► checkout.placeOrder(cart, payment)     ← the ONE simple door
                        │  orchestrates:
        ┌───────┬───────┼────────┬─────────┬──────────┐
     Inventory  Pricing Payments  Shipping  Email    Analytics
   caller doesn't know or care about the six subsystems — just the facade method
🧠
An SDK client is a facade: the Stripe/AWS SDK gives you stripe.charges.create(...) over a pile of HTTP, auth, retries, and serialization. jQuery was a famous facade over inconsistent DOM/AJAX APIs. You call one friendly method; it hides the machinery.
🚪
A hotel concierge: you say "arrange dinner and a taxi at 7," and one person coordinates the restaurant, the car, and the timing. You didn't call three vendors — you used one simplified interface.
A checkout facade coordinating six subsystems
class CheckoutFacade {
  constructor(
    private inventory: Inventory, private pricing: Pricing, private payments: Payments,
    private shipping: Shipping, private email: Mailer, private analytics: Analytics,
  ) {}
  async placeOrder(cart: Cart, payment: PaymentInfo): Promise<Order> {   // the simple door
    await this.inventory.reserve(cart)
    const total = this.pricing.totalFor(cart)
    const receipt = await this.payments.charge(total, payment)
    const order = Order.create(cart, receipt)
    await this.shipping.schedule(order)
    await this.email.sendConfirmation(order)
    this.analytics.track('order.placed', order)
    return order
  }
}
// callers: checkout.placeOrder(cart, payment) — that's the whole surface
🧒
In plain wordsBehind a big task there are often lots of little steps and systems. A facade is a single friendly button that does the whole thing for you — "place the order" — while quietly handling all the steps (stock, payment, shipping, email) in the background. You press one button instead of learning to operate six machines.
🌍
In the wildSDK clients (Stripe, AWS, Twilio) over raw HTTP, jQuery over the DOM, ORMs over SQL, a service-layer/use-case class over multiple repositories, high-level libraries like requests over urllib, and API gateways / backend-for-frontend endpoints that present one call over many microservices. Any "just call this one thing" wrapper over a tangle is a facade.

✅ Do

  • Provide a facade for the common workflows over a complex subsystem
  • Keep the subsystems usable directly for advanced/edge cases
  • Centralize orchestration in the facade so it's changed in one place

❌ Don't

  • Let the facade swell into a God object owning every rule (topic 28)
  • Force everything through the facade if power users need direct access
Gotcha: a facade that keeps absorbing responsibilities becomes a God object (topic 28) — the "simple door" turns into a 2,000-line class every feature must edit, re-coupling everything you meant to decouple. Keep the facade thin: it orchestrates subsystems, it doesn't implement their logic. Also distinguish it from Adapter (topic 8): a facade simplifies an interface for convenience; an adapter converts one interface to a specific other one you're required to match.
11Proxy — a stand-in that controls access▶

Scenario: loading a user's orders from the DB is expensive, and you often don't touch them. An ORM gives you a proxy: a stand-in that looks like the orders collection but only hits the database the moment you actually access it (lazy loading). A proxy has the same interface as the real object but controls access to it.

What

Proxy: a placeholder with the same interface as a real object that controls access to it — adding lazy loading, caching, access control, or remote calls, transparently.

Why

Callers use the object normally while the proxy handles cross-cutting concerns — defer expensive work, cache results, enforce permissions, or make a remote object look local.

How

Implement the target interface; hold (or lazily create) the real subject; intercept calls to add the concern, then delegate.

Same face, controlled access
   caller ──► «Orders» (interface)
                  │
             OrdersProxy   ── first access? ──► load from DB, cache, delegate
                  │         ── cached?      ──► return without touching DB
                  ▼         ── unauthorized?──► throw
             RealOrders (the expensive/remote/protected subject)
🧠
ORM lazy loading is a proxy: Hibernate/ActiveRecord hand you a proxy for a related collection that runs the query only on first access. JavaScript's built-in Proxy intercepts property reads/writes to add validation, logging, or reactivity (Vue's reactivity is built on it).
🛡️
An API gateway / reverse proxy (nginx, Envoy) stands in front of your services, adding auth, rate limiting, caching, and routing — the client thinks it's talking to the service, but the proxy controls access. Same pattern, network scale.
A lazy-loading (virtual) proxy
interface Orders { all(): Promise<Order[]> }

class OrdersProxy implements Orders {                 // same interface as the real thing
  private real?: RealOrders
  private cached?: Order[]
  constructor(private userId: string, private db: Db) {}
  async all(): Promise<Order[]> {
    if (this.cached) return this.cached                // caching concern
    this.real ??= new RealOrders(this.userId, this.db) // lazy-create the subject
    this.cached = await this.real.all()                // defer the expensive query
    return this.cached
  }
}
// user.orders is an OrdersProxy — the DB is hit only when you call .all()
🧒
In plain wordsA proxy is a stand-in that looks and acts exactly like the real thing, but sits in front to control what happens. Maybe it waits to fetch the real thing until you actually need it, or remembers the answer so it doesn't re-fetch, or checks whether you're allowed. You talk to the stand-in as if it were the real object — it quietly manages the access behind the scenes.
🌍
In the wildORM lazy loading (Hibernate/ActiveRecord proxies), JavaScript's Proxy (Vue/MobX reactivity, validation), Spring AOP dynamic proxies (transactions, @Cacheable, security), gRPC/RMI client stubs (remote proxy makes a network object look local), reverse proxies / API gateways (nginx, Envoy) for auth & caching, and CDN edge caches. Protection, virtual (lazy), caching, and remote proxies are the common flavors.

✅ Do

  • Use a proxy to add lazy loading, caching, access control, or remote access transparently
  • Keep the proxy's interface identical to the real subject's
  • Isolate the cross-cutting concern in the proxy, not the business object

❌ Don't

  • Hide expensive/remote work so well that callers get surprise latency (the "N+1 via lazy loading" trap)
  • Put business logic in a proxy — it should only control access
Gotcha: the same transparency that makes proxies elegant hides cost. Lazy-loading proxies are the classic cause of the N+1 query problem (see the N+1 case study): a loop that touches user.orders for 100 users silently fires 100 queries, because each access transparently hits the DB. Proxies also complicate ==/identity (a proxy isn't the real object) and debugging (the object isn't what it appears). Use them deliberately, and know when a proxy is doing expensive work behind an innocent-looking property access.
12Composite — treat trees and leaves uniformly▶

Scenario: a UI is a tree — a Panel contains Buttons and other Panels, nested arbitrarily. You want to call render() (or size()) on the whole tree without special-casing "is this a container or a leaf?" The Composite pattern lets a group of objects be treated the same as a single object.

What

Composite: compose objects into tree structures and let clients treat individual objects (leaves) and compositions (branches) uniformly through one interface.

Why

It removes "is this one thing or a collection?" branching everywhere. Operations recurse naturally, and the tree can nest to any depth.

How

Define one interface (render(), size()); leaves implement it directly; composites implement it by iterating their children and combining results.

Branch and leaf share one interface
          «Component: render()»
                 │
        ┌────────┴─────────┐
     Panel (composite)    Button (leaf)
        │  render() = render each child
     ┌──┴───┐
   Button  Panel ──► Button, Input…      call root.render(); it recurses.
   client code never checks "leaf or container?" — same call works on both
🧠
The DOM and React trees are composites: a <div> holds elements and other divs; you render the root and it recurses. A file system is the same — a directory contains files and directories, and du -sh recurses uniformly over both.
🌲
An org chart: "count reports" works whether you point at an IC (leaf) or a VP (a subtree of managers and ICs). You ask the node; it sums its children. No special case for "manager vs individual."
Leaves and composites, one interface
interface Component { render(): string }

class Button implements Component {                    // leaf
  constructor(private label: string) {}
  render(){ return `[${this.label}]` }
}
class Panel implements Component {                     // composite
  private children: Component[] = []
  add(c: Component){ this.children.push(c); return this }
  render(){ return '(' + this.children.map(c => c.render()).join(' ') + ')' }  // recurse
}
const ui = new Panel().add(new Button('OK')).add(new Panel().add(new Button('Cancel')))
ui.render()   // works on the whole tree — no "leaf or branch?" checks
🧒
In plain wordsThink of folders on your computer: a folder can hold files and other folders, as deep as you like. When you ask "how big is this?", it doesn't matter if you point at a single file or a folder full of folders — you ask, and it adds everything up. Composite lets your code treat "one thing" and "a group of things" exactly the same way, so nested structures just work.
🌍
In the wildThe DOM and React/Vue/Flutter component trees, file systems, UI view hierarchies (Android ViewGroup/View), abstract syntax trees (compilers/linters), org charts, nested menus, scene graphs in games/graphics, and grouped shapes in design tools (group a group). Anytime "a whole" and "a part" respond to the same operations, it's Composite.

✅ Do

  • Use it for genuine part-whole tree hierarchies
  • Put the recursive operation on the interface so branches and leaves share it
  • Let composites combine their children's results

❌ Don't

  • Force leaf objects to implement child-management methods (add/remove) they can't support
  • Use it where the data isn't actually tree-shaped
Gotcha: the design tension is where to put add()/remove(). Put child-management on the shared Component interface and every leaf is forced to implement (or throw on) methods it can't support — an LSP smell (see OOP topic 15). Put it only on Composite and clients must type-check to add children — losing some uniformity. There's no free lunch; pick based on whether callers need to treat everything as a potential container. Also watch recursion on very deep or cyclic trees — guard against stack overflows and cycles.
13Bridge — vary two dimensions independently▶

Scenario: you send notifications of different kinds (alert, reminder, receipt) over different channels (email, SMS, push). If you subclass one per combination you get 3×3 = 9 classes, and adding a channel means adding three more. Bridge splits the two axes — Notification (kind) and Channel (delivery) — so they vary independently: 3 + 3 classes, not 9.

What

Bridge: separate an abstraction from its implementation so the two can vary independently, connecting them by composition instead of a combinatorial class hierarchy.

Why

It prevents the M×N subclass explosion when two dimensions both change. Add a kind or a channel and it's +1 class, not +N.

How

The abstraction holds a reference to an implementor interface and delegates the varying part to it. Compose a kind with a channel at runtime.

Two axes, composed — not multiplied
  ❌ M×N subclasses:                 ✅ bridge (M + N):
   AlertEmail  AlertSms  AlertPush    «Notification» ──has-a──► «Channel»
   ReminderEmail ReminderSms …           Alert                    EmailChannel
   ReceiptEmail  …  (9, then 12…)         Reminder                 SmsChannel
                                          Receipt                  PushChannel
   add a channel → +3 classes         add a channel → +1 class. axes are independent.
🧠
Device drivers bridge OS and hardware: the OS's "printing" abstraction is separate from each printer's driver (implementor). Add a printer → add a driver, not a new OS print subclass. JDBC is the same: the API (abstraction) is separate from each database driver (implementation).
🔀
Cross-platform rendering: a shape/UI abstraction vs the rendering backend (Canvas, SVG, OpenGL). The remote control (abstraction) works with any TV brand (implementation) because they're bridged, not fused.
Notification kind × delivery channel, composed
interface Channel { deliver(to: string, text: string): Promise<void> }   // implementor
class EmailChannel implements Channel { async deliver(to,t){ /* SES */ } }
class SmsChannel   implements Channel { async deliver(to,t){ /* Twilio */ } }

abstract class Notification {                        // abstraction, holds a Channel
  constructor(protected channel: Channel) {}          // the "bridge"
  abstract send(user: User): Promise<void>
}
class Alert extends Notification {
  async send(user: User){ await this.channel.deliver(user.contact, '⚠ Alert: …') }
}
class Receipt extends Notification {
  async send(user: User){ await this.channel.deliver(user.contact, 'Your receipt: …') }
}
// compose freely: new Alert(new SmsChannel());  new Receipt(new EmailChannel())
// add a channel → one class; add a notification kind → one class. no M×N.
🧒
In plain wordsWhen two things both change — what you're sending and how you're sending it — don't make a separate class for every pairing (that's a huge grid). Instead, keep the "what" and the "how" as two separate dials and snap them together. Then adding a new "how" (say, WhatsApp) is one new piece that works with every "what," instead of one new piece per combination.
🌍
In the wildJDBC/ODBC (API bridged to DB drivers), device driver models, cross-platform GUI/rendering backends (an app UI vs Canvas/SVG/GPU), notification systems (message type × channel), payment (transaction type × gateway), and persistence abstractions over multiple stores. Whenever you catch an M×N subclass grid forming, Bridge collapses it to M+N.

✅ Do

  • Use it when two dimensions genuinely vary independently
  • Connect abstraction and implementor by composition, injected at runtime
  • Reach for it when you see an M×N subclass explosion forming

❌ Don't

  • Introduce a bridge for one dimension that varies (that's over-engineering)
  • Confuse it with Adapter — Bridge is designed up front; Adapter retrofits an existing mismatch
Gotcha: Bridge is easy to confuse with Strategy and Adapter because all three use composition. The distinction: Strategy (topic 15) swaps one algorithm behind an interface; Bridge separates two independently-varying dimensions (abstraction and implementation); Adapter (topic 8) retrofits a mismatch between existing interfaces you didn't design together. Bridge is a deliberate, up-front split for anticipated two-axis variation — applying it to a single axis, or before you actually have both dimensions varying, just adds indirection you don't need yet (topic 28).
14Flyweight — share to save memory▶

Scenario: a text editor rendering a million characters. Giving every character its own object with font, size, and glyph metrics would blow up memory. The Flyweight pattern shares the intrinsic state (the glyph "A" at 12pt Arial is one shared object) and passes the extrinsic state (its position on the page) from outside — so a million characters reuse a few dozen glyph objects.

What

Flyweight: minimize memory by sharing the common, immutable part (intrinsic state) of many similar objects, and supplying the variable part (extrinsic state) externally per use.

Why

When you have huge numbers of similar objects, sharing the identical portion turns millions of objects into a small pool plus lightweight references.

How

Split state into intrinsic (shared, cached in a factory) and extrinsic (passed in by the caller). A factory returns the shared flyweight for a given key.

Share the identical part; pass the rest in
   1,000,000 characters on screen
        │  each needs: glyph + font (intrinsic)  +  x,y position (extrinsic)
        ▼
   Glyph('A',12pt,Arial)  ← ONE shared object, reused everywhere 'A' appears
        used at (0,0), (14,0), (28,0)…  ← positions passed in, not stored per-char
   memory: ~dozens of glyph objects, not a million
🧠
String interning is flyweight: Java/Python/C# keep one shared instance of identical string literals instead of duplicating them. Browsers cache one glyph per character/font and stamp it at many positions. Same principle: store the identical thing once.
🎮
Game tile/particle sharing: a forest of 10,000 trees shares a handful of tree models/textures (intrinsic); each instance only stores its position and scale (extrinsic). That's how huge scenes fit in memory.
A glyph flyweight factory shares intrinsic state
class Glyph {                                 // intrinsic (shared, immutable) state
  constructor(readonly char: string, readonly font: string, readonly size: number) {}
  drawAt(x: number, y: number){ /* render this glyph at an EXTRINSIC position */ }
}
class GlyphFactory {
  private pool = new Map<string, Glyph>()
  get(char: string, font: string, size: number): Glyph {
    const key = `${char}|${font}|${size}`
    let g = this.pool.get(key)
    if (!g){ g = new Glyph(char, font, size); this.pool.set(key, g) }  // create once
    return g                                                            // reuse forever
  }
}
// a million 'A's → one Glyph('A',...) object; positions passed to drawAt(x,y)
🧒
In plain wordsIf you need a zillion things that are mostly the same, don't store a full copy of each. Keep one master copy of the shared part and just remember the little differences (like where each one goes). Like a rubber stamp: you have one stamp for the letter "A" and press it wherever you need an A — you don't carve a brand-new "A" a million times.
🌍
In the wildString interning (Java String.intern(), Python small-int/string caching, JS Symbol), browser glyph/font caches and text rendering, game engines sharing meshes/textures/tiles, immutable shared config, Integer.valueOf's cached small integers, and icon/sprite atlases. Anywhere "millions of nearly-identical objects" would otherwise blow memory, flyweight sharing appears.

✅ Do

  • Use it when object count is huge and much of the state is shared & immutable
  • Cleanly separate intrinsic (shared) from extrinsic (per-use) state
  • Keep flyweights immutable so sharing is safe

❌ Don't

  • Apply it when you have few objects (the factory/complexity isn't worth it)
  • Store mutable per-instance data in a shared flyweight (corrupts every user)
Gotcha: flyweights must be immutable — since one object is shared by thousands of users, any mutable field would let one caller's change corrupt everyone else's. The whole pattern hinges on the shared (intrinsic) state being read-only. Also, it's a memory optimization with real complexity cost (a factory, split state, extrinsic threading through call sites) — only worth it when profiling shows object count is genuinely the problem. Modern GC and value types handle most cases; reach for Flyweight for the extreme end (millions of objects), not routinely.

15Strategy — swap the algorithm at runtime★ core▶

Scenario: shipping cost is computed differently per carrier (flat, weight-based, zone-based). Baking all three into one method with a switch means editing it for every new carrier. Strategy makes each algorithm a separate interchangeable object, injected into the context: new Checkout(new WeightBasedShipping()).

What

Strategy: define a family of interchangeable algorithms behind one interface and let the client pick/swap which one to use at runtime.

Why

It removes algorithm-selection if/switch ladders, makes each algorithm independently testable, and lets you add a new one without touching the others (Open/Closed).

How

Define a strategy interface; implement one class per algorithm; the "context" holds a strategy and delegates the varying step to it. Inject the choice.

One interface, interchangeable algorithms
   Checkout(context) ──► «ShippingStrategy.cost(order)»
                                 ▲          ▲          ▲
                          FlatRate   WeightBased   ZoneBased
   swap at runtime: checkout.setStrategy(new ZoneBased())
   add a carrier → new class implementing the interface. context unchanged.
🧠
A sort comparator is a strategy: arr.sort(byPrice) vs arr.sort(byName) — same sort algorithm, pluggable comparison function. In languages with first-class functions, a strategy is often just a function you pass in.
🔧
Passport.js auth strategies, compression algorithm selection (gzip vs brotli), and pluggable pricing/tax/discount rules are all Strategy — the surrounding flow is fixed; one decision step is swappable.
Shipping strategies, injected into the context
interface ShippingStrategy { cost(order: Order): Money }
class FlatRate     implements ShippingStrategy { cost(o){ return Money.of(5,'USD') } }
class WeightBased  implements ShippingStrategy { cost(o){ return Money.of(o.weightKg*2,'USD') } }
class ZoneBased    implements ShippingStrategy { cost(o){ /* by destination */ } }

class Checkout {
  constructor(private shipping: ShippingStrategy) {}   // the strategy is injected
  quote(order: Order){ return order.total().add(this.shipping.cost(order)) }
}
new Checkout(new WeightBased()).quote(order)     // pick per carrier at runtime
// in JS you'd often just pass a function: (order) => Money.of(order.weightKg*2,'USD')
🧒
In plain wordsWhen there are several ways to do one step — like several ways to calculate shipping — make each way its own little swappable module and plug in whichever you want. The rest of the checkout doesn't change; you just hand it a different "how to calculate shipping" piece. Adding a new way is adding a new piece, not rewiring the machine.
🌍
In the wildSort comparators (Comparator, sort(key=…)), Passport.js auth strategies, pricing/tax/discount/shipping rule engines, compression/encryption algorithm selection, retry/backoff policies, and ML model selection. In functional languages Strategy collapses into "pass a function," which is why higher-order functions are said to subsume it.

✅ Do

  • Use it when one step has several interchangeable algorithms
  • Inject the strategy so it's swappable and testable
  • In FP-friendly languages, pass a function instead of a whole class

❌ Don't

  • Create a strategy hierarchy for a single algorithm that never varies
  • Re-introduce a switch to pick the strategy in the context itself
Gotcha: Strategy, Bridge, and State look alike (all delegate to a composed object). Strategy is about interchangeable algorithms for one step, chosen by the client; State (topic 19) is about an object changing its own behavior as its state changes (and often switching itself); Bridge (topic 13) separates two independent dimensions. Also: in a language with first-class functions, a full Strategy class per algorithm is usually overkill — pass a lambda. Reserve the class form for strategies that carry configuration/state or need naming.
16Observer — publish changes to many listeners★ everywhere▶

Scenario: when an order ships, several things must react — email the customer, update analytics, notify the warehouse — and you'll keep adding reactions. Hard-coding all of them into ship() couples it to everything. Observer lets the order publish an event and any number of subscribers react, without the publisher knowing who's listening.

What

Observer: a subject maintains a list of observers and notifies them automatically when its state changes, so many objects react to one event without tight coupling.

Why

The publisher stays decoupled from reacters — add/remove listeners freely. It's the backbone of event-driven UIs and reactive systems.

How

Subject exposes subscribe/unsubscribe; on change it iterates observers and calls their handler. Observers register interest and react.

One event, many independent reacters
   Order.ship()  ──emit('shipped')──►  observers notified:
                                          ├─ EmailObserver.on(e)   → send email
                                          ├─ AnalyticsObserver.on(e)→ track
                                          └─ WarehouseObserver.on(e)→ update stock
   the Order doesn't know who's listening. add/remove observers without touching it.
🧠
DOM events are Observer: element.addEventListener('click', handler) — many handlers subscribe; the element notifies them all on click. Node's EventEmitter, RxJS Observables, and Redux store.subscribe are the same subscribe-and-get-notified shape.
📰
A newsletter: subscribers register; when an issue drops, everyone gets it. The publisher doesn't tailor sends or know each subscriber — it just notifies the list. Unsubscribe and you stop hearing about it.
A subject that notifies its observers
type Handler<T> = (event: T) => void
class Subject<T> {
  private observers = new Set<Handler<T>>()
  subscribe(h: Handler<T>){ this.observers.add(h); return () => this.observers.delete(h) } // returns unsubscribe
  notify(event: T){ this.observers.forEach(h => h(event)) }
}
const shipped = new Subject<Order>()
shipped.subscribe(o => mailer.sendShipped(o))       // add reactions freely,
shipped.subscribe(o => analytics.track('shipped', o)) // without editing the publisher
// on ship: shipped.notify(order)
🧒
In plain wordsOne thing happens (an order ships) and lots of others want to know. Instead of the order personally telling each one, it just shouts "shipped!" and anyone who signed up to listen reacts on their own. You can add new listeners (or remove them) anytime, and the order never has to change — it doesn't even know who's listening.
🌍
In the wildDOM addEventListener, Node EventEmitter, RxJS/Reactive Extensions, Redux/Vuex subscribe, React state + useEffect (components observe state), MobX/Vue reactivity, model→view notifications in MVC, and database change streams / websockets. It's the in-process cousin of Pub/Sub (topic 26), which distributes the same idea across services.

✅ Do

  • Use it when many objects must react to one object's changes
  • Return/track an unsubscribe handle to avoid leaks
  • Keep observer handlers small and side-effect-focused

❌ Don't

  • Forget to unsubscribe (the #1 memory-leak source in UIs)
  • Build long chains where observers trigger observers trigger observers (hard to trace)
Gotcha: the two classic bugs are leaks and invisible cascades. Forgetting to unsubscribe keeps dead objects alive (React's useEffect cleanup exists precisely for this); and when observers themselves emit events that trigger more observers, you get cascading updates that are hard to trace and can even loop infinitely. Notification order is also usually undefined — don't rely on observer A running before B. For cross-service fan-out, don't hand-roll Observer; use a real Pub/Sub broker (topic 26) with delivery guarantees.
17Command — actions as objects★ powerful▶

Scenario: you need undo/redo in an editor, and a background job queue where work runs later on another machine. Both need the same thing: an action turned into an object you can store, pass around, queue, log, and replay. That's the Command pattern — encapsulate "do this" (and often "undo this") as a first-class object.

What

Command: wrap a request/action as an object with an execute() (and often undo()), decoupling the thing that invokes an action from the thing that performs it.

Why

Actions become storable and manipulable: queue them, log them, schedule them, retry them, and undo them. It's the basis of job queues, undo stacks, and CQRS commands.

How

Each action is a class with execute() capturing its parameters/receiver. An invoker runs (or queues/logs) commands without knowing their concrete type.

Package an action so you can queue/log/undo it
   «Command { execute()  undo() }»
        ├─ ChargeCard(order, amount)     ─► queue → run on a worker later
        ├─ AddItem(cart, product)        ─► push on undo-stack; undo() reverses it
        └─ SendEmail(to, template)       ─► log → retry on failure
   invoker just calls cmd.execute(); it doesn't know WHAT the command does
🧠
Job queues are Command: each enqueued job (Sidekiq, Celery, BullMQ, SQS message) is a serialized action — receiver + params — executed later, elsewhere, with retries. Redux actions are commands too: plain objects describing "what to do."
↩️
Undo/redo keeps a stack of command objects; undo() pops and reverses the last one. A restaurant order ticket is a command: it captures the request, gets queued, and the kitchen (receiver) executes it — decoupled from the waiter (invoker).
Commands with execute + undo (undo/redo & queues)
interface Command { execute(): void; undo(): void }

class AddItem implements Command {                      // an action as an object
  constructor(private cart: Cart, private product: Product) {}
  execute(){ this.cart.add(this.product) }
  undo(){ this.cart.remove(this.product) }
}
class History {                                         // invoker + undo stack
  private done: Command[] = []
  run(c: Command){ c.execute(); this.done.push(c) }
  undo(){ this.done.pop()?.undo() }
}
// queue variant: serialize commands and run them on a worker later (job queue)
🧒
In plain wordsInstead of just doing something right now, you write the action down on a card — "add this item," "charge this card" — and hand the card off. Now you can stack the cards to undo them, put them in a to-do line to run later, or keep a copy in case you need to retry. Turning "do X" into a physical thing you can hold is what makes undo, queues, and scheduling possible.
🌍
In the wildJob/task queues (Sidekiq, Celery, BullMQ, SQS, Kafka consumers), undo/redo stacks in editors (VS Code, Photoshop), Redux actions & CQRS commands, database transaction logs / write-ahead logs (replayable commands), keybinding→command maps, macro recording, and the Command bus in DDD apps. Serializable commands are what make "run it later, elsewhere, and retry" possible.

✅ Do

  • Use it for undo/redo, queuing, scheduling, logging, and retry of actions
  • Capture everything the action needs so it can run later/elsewhere
  • Add undo() when you need reversibility

❌ Don't

  • Wrap a plain immediate function call in a Command for no reason
  • Store un-serializable references in a command you intend to queue/persist
Gotcha: undo is deceptively hard. A command that captured the wrong thing can't reverse itself: to undo "delete row," you must have saved the row's prior state (which drifts into the Memento pattern, topic 23). And commands meant to be queued/persisted must be serializable — capturing a live DB connection or a closure over huge objects breaks "run it later on another worker." Design commands to carry plain data (ids, params), resolve receivers at execution time, and store enough state to reverse — or accept that some commands are execute-only.
18Chain of Responsibility — pass it down the line▶

Scenario: an incoming HTTP request must pass through auth, rate-limiting, logging, and body-parsing before reaching your handler — and each step may pass it on or stop it. Chain of Responsibility links handlers so a request flows down the chain until one handles it (or all get a turn). This is web middleware.

What

Chain of Responsibility: pass a request along a chain of handlers; each decides to handle it, transform it, and/or forward it to the next — decoupling sender from the specific receiver.

Why

You can add, remove, or reorder handling steps without touching the others, and no single place needs to know the whole pipeline.

How

Each handler holds a reference to the next and calls it (or short-circuits). Assemble the chain in order; feed the request to the head.

Request flows down until handled/stopped
   request ─► Auth ─► RateLimit ─► Logging ─► BodyParser ─► Handler
                │         │  (429?     │ next()      │            │
              next()   stop!)        next()        next()      respond
   any link can handle-and-stop or transform-and-forward. reorder freely.
🧠
Express/Koa/Rack middleware and Servlet filters ARE this pattern: each middleware gets (req, res, next) and either responds or calls next() to pass control down the chain. It's the everyday face of Chain of Responsibility.
🎫
An approval/escalation chain: a purchase request goes to your manager; if it's over their limit they pass it up to the director, then the VP — each either approves or forwards. Support tiers (L1→L2→L3) work the same way.
A middleware-style handler chain
type Ctx = { req: Request; res: Response }
type Handler = (ctx: Ctx, next: () => void) => void

function chain(handlers: Handler[]) {
  return (ctx: Ctx) => {
    let i = -1
    const dispatch = () => { i++; if (i < handlers.length) handlers[i](ctx, dispatch) }
    dispatch()
  }
}
const auth: Handler      = (c, next) => c.req.user ? next() : c.res.status(401)  // stop
const rateLimit: Handler = (c, next) => underLimit(c) ? next() : c.res.status(429)
const app = chain([auth, rateLimit, /* logging, */ handler])  // reorder freely
🧒
In plain wordsLine up a series of checkpoints, and send the request down the line. Each checkpoint can deal with it and stop, or tweak it and wave it on to the next. Nobody needs to know the whole line — each just knows "handle or pass along." That's exactly how a web server runs a request through login-check, rate-limit, logging, and finally your code.
🌍
In the wildExpress/Koa/Connect middleware, Rack (Ruby), ASP.NET Core middleware, Java Servlet Filters, logging handler levels, DOM event bubbling/capture, exception-handler chains, ETL/processing pipelines, and approval/escalation workflows. Reordering or inserting a step without touching the rest is the everyday payoff.

✅ Do

  • Use it for pipelines where steps can handle, transform, or forward
  • Keep each handler single-purpose and order the chain explicitly
  • Allow short-circuiting (a handler that stops the chain)

❌ Don't

  • Build a chain where no handler ever handles the request (it falls off the end silently)
  • Hide critical control flow across so many links it's impossible to follow
Gotcha: two failure modes. First, a request can fall off the end unhandled — if every link forwards and none handles, you get silent no-ops or hangs (in middleware, forgetting to call next() or to respond hangs the request). Second, order is load-bearing and implicit: put logging before auth and you log unauthenticated noise; put body-parsing after the handler and it's too late. Make the chain's order explicit and tested, ensure a terminal handler always exists, and guarantee each link either forwards or completes.
19State — behavior that changes with state★ core▶

Scenario: an Order behaves differently depending on its status — you can pay a pending order, cancel a paid one, but not cancel a shipped one. Encoding this as if (status === …) checks scattered across every method is bug-prone. The State pattern makes each state an object that defines what's allowed and where you can transition.

What

State: let an object alter its behavior when its internal state changes, by delegating to a state object — so it "appears to change class." Each state encapsulates its allowed actions and transitions.

Why

It replaces sprawling status-conditionals with explicit states, makes illegal transitions impossible, and puts each state's rules in one place — a real state machine.

How

Model each state as a class/object implementing the same interface; the context delegates actions to its current state, which may switch the context to a new state.

Each state defines allowed actions + transitions
   Pending ──pay()──► Paid ──ship()──► Shipped ──deliver()──► Delivered
      │  cancel() → Cancelled   │ cancel() → refund+Cancelled   │ cancel()? ❌ blocked
   each state OBJECT knows: which actions are legal + where they lead.
   context.cancel() delegates to current state — no scattered status ifs.
🧠
TCP is a state machine: LISTEN → SYN-RCVD → ESTABLISHED → FIN-WAIT… each state permits different packets. A Promise is too: pending → fulfilled/rejected, and .then behaves per state. Workflow engines and game AI use explicit state objects.
🚦
A traffic light only transitions Green→Yellow→Red→Green, and each state dictates behavior. Libraries like XState (JS) and Spring StateMachine make these explicit precisely because if-soup state logic is so error-prone.
Order states as objects with explicit transitions
interface OrderState { pay(o: Order): void; cancel(o: Order): void }

class Pending implements OrderState {
  pay(o){ o.setState(new Paid()) }
  cancel(o){ o.setState(new Cancelled()) }
}
class Paid implements OrderState {
  pay(o){ throw new Error('already paid') }
  cancel(o){ o.refund(); o.setState(new Cancelled()) }
}
class Shipped implements OrderState {
  pay(o){ throw new Error('already paid') }
  cancel(o){ throw new Error('cannot cancel a shipped order') }   // illegal transition
}
class Order { constructor(private state: OrderState = new Pending()){}
  setState(s: OrderState){ this.state = s }
  pay(){ this.state.pay(this) }  cancel(){ this.state.cancel(this) } }
🧒
In plain wordsSome things act differently depending on what "mode" they're in — an order that's just been placed can be paid or cancelled, but one that's already shipped can't be cancelled. Instead of scattering "if it's in this mode, then…" checks everywhere, give each mode its own rulebook that says what you can do and what mode you move to next. The order just asks its current mode what to do.
🌍
In the wildOrder/subscription/payment lifecycles, TCP connection states, JavaScript Promises (pending/fulfilled/rejected), workflow & approval engines, game AI (patrol/chase/flee), CI/CD pipeline stages, document review flows, and dedicated libraries like XState, Spring StateMachine, and AWS Step Functions. Anywhere "what's allowed depends on current status," an explicit state machine beats scattered conditionals.

✅ Do

  • Use it when behavior and allowed actions depend on a lifecycle status
  • Make each state own its legal actions and transitions
  • Reach for a state-machine library when transitions get complex

❌ Don't

  • Scatter if (status === …) checks across many methods
  • Model a boolean flag with two behaviors as a heavyweight state hierarchy
Gotcha: State vs Strategy again — structurally identical (delegate to a composed object), different intent. Strategy's object is chosen by the client and doesn't change itself; State's object is switched by the states themselves as the object progresses through a lifecycle. The real-world trap is where transitions live: if each state hard-codes its next states, the transition map is scattered across classes and hard to see whole. For non-trivial machines, keep the transition table explicit (or use a state-machine library) so the full set of legal transitions is visible and testable in one place.
20Template Method — fixed skeleton, pluggable steps▶

Scenario: every data importer does the same dance — open source, read rows, parse (CSV vs JSON vs XML differs), validate, write to DB, close. The skeleton is identical; only a step or two vary. Template Method defines the skeleton in a base class and lets subclasses fill in specific steps (hook methods).

What

Template Method: define the skeleton of an algorithm in a method, deferring some steps to subclasses via overridable hook methods — the overall structure is fixed, specific steps vary.

Why

It removes duplicated boilerplate around the varying bits and enforces a consistent overall flow (the base controls the sequence; subclasses only fill blanks).

How

A concrete base method calls a sequence of steps, some abstract/overridable. Subclasses override just the steps that differ; they don't touch the sequence.

Base owns the sequence; subclass fills steps
   Importer.run()  (template method — fixed skeleton)
     open()          ← shared
     rows = read()   ← shared
     parse(rows)     ← ABSTRACT hook  ► CsvImporter / JsonImporter override
     validate()      ← shared
     write()         ← shared (or hook)
     close()         ← shared
   subclass changes parse(); it CANNOT reorder or skip the skeleton steps
🧠
Framework lifecycle hooks are template methods: React/Android call their fixed lifecycle and invoke your render()/onCreate(); test frameworks call setUp()/your test/tearDown() in a fixed order. Rails callbacks (before_save) hook into a fixed persistence flow.
📋
A recipe template: "prep → cook → plate" is fixed; the "cook" step differs per dish. You override the step, not the sequence. It's the Hollywood principle — "don't call us, we'll call you" — the framework drives; your hooks get called.
A fixed import skeleton with an overridable parse step
abstract class Importer {
  run(source: string) {                         // the TEMPLATE METHOD (fixed flow)
    const raw = this.open(source)
    const rows = this.parse(raw)                 // ← the varying step (hook)
    const valid = rows.filter(r => this.validate(r))
    this.write(valid)
    this.close()
  }
  protected abstract parse(raw: string): Row[]   // subclasses fill this in
  protected open(s: string){ /* shared */ return read(s) }
  protected validate(r: Row){ return r.id != null }   // shared default (overridable)
  protected write(rows: Row[]){ /* shared */ }
  protected close(){ /* shared */ }
}
class CsvImporter  extends Importer { parse(raw){ return csv(raw) } }   // only the diff
class JsonImporter extends Importer { parse(raw){ return JSON.parse(raw) } }
🧒
In plain wordsLots of jobs follow the same steps in the same order, with just one or two steps done differently. So write the step-by-step plan once, but leave a couple of blanks for the parts that change. Each specific version just fills in the blanks — it can't reshuffle the plan. Like a fill-in-the-blank recipe where only the "which spice" line changes.
🌍
In the wildFramework lifecycle hooks (React/Android/servlet lifecycles), test setUp/tearDown, Rails/Django model callbacks, Spring's JdbcTemplate/RestTemplate (they own the resource dance; you supply the query/mapper), sorting frameworks that call your comparator, and ETL/build-pipeline skeletons. It's the inheritance-based cousin of Strategy (which composes the varying step instead of overriding it).

✅ Do

  • Use it when many variants share one algorithm skeleton with a few varying steps
  • Keep the sequence in the base; expose only the intended hook points
  • Provide sensible default hooks subclasses can optionally override

❌ Don't

  • Expose so many hooks that subclasses effectively rewrite the algorithm
  • Reach for inheritance here if composition (Strategy) fits better and is more flexible
Gotcha: Template Method is inheritance-based, so it inherits inheritance's downsides (OOP topics 4, 6): a change to the base skeleton can break every subclass (fragile base class), and a subclass is locked to one parent. Many modern codebases prefer the composition alternative — pass the varying step in as a Strategy/function (e.g. importer(source, parseFn)) — which is more flexible and testable. Use Template Method when the shared flow is genuinely stable and the variation is naturally expressed by subtyping; otherwise inject the step.
21Iterator — traverse without exposing internals▶

Scenario: you want to loop over a collection — an array, a tree, a paginated API, a database cursor — without caring how it stores its elements. The Iterator pattern provides a uniform way to walk a collection one element at a time, hiding whether it's backed by an array, a linked list, or lazy pages.

What

Iterator: provide a standard way to access elements of a collection sequentially without exposing its underlying representation.

Why

Client code uses one loop shape (for…of) over any collection, and you can iterate lazily (generators, streams, paginated data) without loading everything at once.

How

Expose an iterator with next() (returning value + done), or implement the language's iterable protocol / a generator, so standard loops work.

One loop shape over any backing structure
   for (const x of collection) { … }
                │  works the same whether collection is:
     ┌──────────┼───────────┬───────────────┬──────────────┐
   Array     LinkedList   Tree (in-order)  DB cursor    Paginated API
   the iterator hides HOW elements are stored/fetched; caller just walks them
🧠
It's built into the language: JS Symbol.iterator + for…of, Python __iter__/generators, Java Iterator/Iterable, C# IEnumerable/yield. Database cursors and Node streams iterate huge/lazy data without loading it all.
📼
Generators are lazy iterators: function* yields values on demand — perfect for infinite sequences or streaming a million rows one at a time, so you never hold the whole thing in memory.
A custom iterable + a lazy generator
class Tree {
  constructor(public value: number, public children: Tree[] = []) {}
  *[Symbol.iterator](): Iterator<number> {          // implement the iterable protocol
    yield this.value
    for (const child of this.children) yield* child     // recurse lazily
  }
}
for (const v of new Tree(1, [new Tree(2), new Tree(3)])) console.log(v)  // 1,2,3

// lazy pagination — walk an API without loading every page up front
async function* pages(url: string){
  let next = url
  while (next){ const r = await fetch(next).then(x=>x.json()); yield* r.items; next = r.next }
}
🧒
In plain wordsYou want to go through a bunch of things one by one, without needing to know how they're stored inside. An iterator is like a tour guide that just says "here's the next one… and the next…" until there are no more. The same "give me the next one" works whether it's a simple list, a tree, or pages coming from a website — and it can fetch things only as you ask, instead of all at once.
🌍
In the wildEvery language's for…of/foreach, generators (function*, Python yield), database cursors (stream rows without loading the table), Node/Java streams, paginated API iteration, RxJS/reactive sequences, and tree/graph traversals. Iterator is so fundamental it's a built-in language protocol almost everywhere — you implement it, you don't reinvent it.

✅ Do

  • Implement your language's iterable protocol so standard loops work
  • Use lazy iterators/generators for large or streaming data
  • Hide the backing structure behind the iterator

❌ Don't

  • Expose internal arrays/nodes for callers to traverse manually
  • Mutate a collection while iterating it (a classic invalidation bug)
Gotcha: modifying a collection while iterating it is the perennial bug — many languages throw ConcurrentModificationException or produce skipped/duplicated elements (JS iterating and splice-ing an array, Python mutating a dict mid-loop). Collect changes and apply them after, or iterate a copy. Second gotcha: lazy iterators are single-pass and stateful — a generator, DB cursor, or stream is consumed once; iterating it again yields nothing. If you need multiple passes, materialize it (to an array) or create a fresh iterator each time.
22Mediator — centralize many-to-many chatter▶

Scenario: a complex form where changing the country dropdown updates the state list, toggles a tax field, and enables/disables Submit. If every widget talks directly to every other widget, you get an N×N tangle. A Mediator puts one coordinator in the middle: widgets report to it, and it orchestrates who updates whom.

What

Mediator: define an object that encapsulates how a set of objects interact, so they refer to the mediator instead of each other — turning many-to-many coupling into a hub-and-spoke.

Why

It untangles N objects each knowing about the others (N² links) into N objects knowing one mediator. Interaction logic lives in one place, not smeared across components.

How

Components notify the mediator of events; the mediator holds the coordination rules and tells the relevant components what to do. Components don't reference each other.

Hub-and-spoke instead of an N×N mesh
  ❌ every widget ↔ every widget:        ✅ mediator hub:
     Country ── State                     Country ─┐
        │  ╲  ╱  │                        State  ──┤
     Tax ─── Submit  (tangled mesh)       Tax    ──┼─► Mediator (coordination rules)
                                          Submit ──┘
   N² connections → N connections to one coordinator; rules centralized
🧠
Air traffic control is the classic mediator: planes don't negotiate directly with each other — they all talk to the tower, which coordinates. A chat room mediates between participants; nobody wires peer-to-peer.
🎛️
A Redux/Vuex store acts as a mediator for UI components: components dispatch to the store and read from it, rather than talking to each other. The store centralizes the interaction logic and state.
A form mediator coordinating widgets
class FormMediator {
  constructor(private country: Select, private state: Select,
              private tax: Field, private submit: Button) {}
  notify(sender: string, event: string) {                 // components report here
    if (sender === 'country' && event === 'change') {
      this.state.loadFor(this.country.value)              // mediator decides the ripple
      this.tax.setVisible(this.country.value === 'US')
      this.submit.setEnabled(this.country.value !== '')
    }
  }
}

🧒
In plain wordsWhen lots of parts all need to talk to lots of other parts, it becomes a spaghetti mess. So you put one coordinator in the middle — everyone talks only to it, and it tells the right parts what to do. Like air traffic control: planes don't call each other, they all talk to the tower, and the tower keeps everyone organized.
🌍
In the wildRedux/Vuex/NgRx stores mediating components, air-traffic-control-style coordinators, chat servers, UI dialog controllers coordinating widgets, MVC/MVP controllers/presenters, and (at service scale) message brokers / API gateways coordinating microservices. Note: an in-app event bus blurs into Pub/Sub (topic 26) — Mediator is about centralized coordination logic, not just message passing.

✅ Do

  • Use it when many components interact in complex ways
  • Centralize the interaction rules in the mediator
  • Keep components referencing only the mediator, not each other

❌ Don't

  • Let the mediator absorb all logic and become a God object (topic 28)
  • Use it for simple one-to-one interactions that don't need coordination
Gotcha: the mediator's whole job is to hold coordination complexity — which means it tends to grow into a God object (topic 28). You untangled the components, but if you're not careful you concentrated all that tangle into one 1,500-line coordinator that every feature must edit. Keep it focused on coordination, push real domain logic into the components/services, and split the mediator when it spans unrelated concerns. Also distinguish it from Observer/Pub-Sub: Mediator centralizes who-tells-whom-what logic; a bare event bus just delivers messages without the coordination rules.
23Memento — capture & restore state (undo)▶

Scenario: a document editor needs undo. You must snapshot the document's state before each change and restore it later — without exposing or breaking the document's encapsulation. The Memento pattern captures an object's internal state into an opaque token you can stash and later use to roll back.

What

Memento: capture an object's internal state in a token (the memento) that can be stored externally and used to restore the object later, without violating its encapsulation.

Why

It's how you implement undo/redo, checkpoints, and rollbacks: save known-good snapshots and return to them, while the object keeps its internals private.

How

The object creates a memento of its state and can restore from one; a "caretaker" (e.g. an undo stack) holds mementos but treats them as opaque.

Snapshot now, roll back later
   Editor.save()   ──► Memento{ text, cursor }  ──► pushed onto undo-stack (caretaker)
   ...user edits...
   Editor.undo()   ◄── pop Memento  ◄── restore(state)
   caretaker holds snapshots but can't read/alter them — encapsulation preserved
🧠
Game save states and DB savepoints are mementos: capture everything needed to resume/rollback to a point. A VM/container snapshot or a filesystem snapshot (ZFS, Time Machine) is the same idea at a different scale.
↩️
Undo/redo stacks pair Memento with Command (topic 17): commands do the work; mementos remember the before-state so undo() can restore it. React's state snapshots and form "reset to saved" work this way.
Editor snapshots + an undo caretaker
class EditorMemento { constructor(readonly text: string, readonly cursor: number) {} }

class Editor {
  private text = ''; private cursor = 0
  type(s: string){ this.text += s; this.cursor += s.length }
  save(): EditorMemento { return new EditorMemento(this.text, this.cursor) }  // snapshot
  restore(m: EditorMemento){ this.text = m.text; this.cursor = m.cursor }     // roll back
}
class History {                                   // caretaker — holds opaque mementos
  private stack: EditorMemento[] = []
  backup(e: Editor){ this.stack.push(e.save()) }
  undo(e: Editor){ const m = this.stack.pop(); if (m) e.restore(m) }
}
🧒
In plain wordsBefore you change something, take a snapshot — like a save point in a video game. Keep the snapshots in a pile. If you mess up, grab the last snapshot and go back to exactly how things were. The nice part: the snapshot is a sealed package — the pile that stores it doesn't get to peek inside or mess with the object's private stuff.
🌍
In the wildUndo/redo in editors (VS Code, Word, Figma), game save states, database savepoints and transaction rollback, VM/container/filesystem snapshots (ZFS, Time Machine), React/form "reset to saved," event-sourcing snapshots, and browser history state. Often paired with Command (topic 17) to build a full undo system.

✅ Do

  • Use it for undo/redo, checkpoints, and rollback
  • Keep the memento opaque to the caretaker (only the originator reads it)
  • Snapshot only the state you actually need to restore

❌ Don't

  • Snapshot huge state on every keystroke without limits (memory blowup)
  • Let external code depend on the memento's internal shape
Gotcha: naïve Memento is a memory hog — full snapshots of large state on every change can balloon fast. Real systems bound it: cap the undo stack, snapshot at intervals, or store diffs instead of full copies (which shades into the Command pattern's "store the reverse operation"). There's also a deep-copy trap identical to Prototype's (topic 6): if the memento holds references into the live object's mutable internals instead of a copy, later edits corrupt your "saved" snapshot. Capture an immutable, deep copy of exactly the state you need to restore — no more, no less.
24Visitor — add operations to a type hierarchy▶

Scenario: you have an AST (abstract syntax tree) of node types — NumberLit, BinaryOp, FunctionCall — and you keep needing new operations over it: evaluate, pretty-print, type-check, minify. Adding each as a method on every node type bloats the nodes. Visitor lets you add new operations without touching the node classes — each operation is a separate visitor.

What

Visitor: represent an operation to perform on the elements of an object structure as a separate visitor object, so you can add new operations without changing the element classes.

Why

When the set of types is stable but you add operations often (compilers, linters), Visitor keeps each operation in one cohesive place instead of scattering it across every type.

How

Each element has accept(visitor) that calls the visitor's method for its type (double dispatch). Each operation is one visitor implementing a method per element type.

Operations live in visitors, not in the nodes
   AST nodes (stable):   NumberLit   BinaryOp   FunctionCall
        each has accept(v) ─► calls v.visitNumberLit(this) etc. (double dispatch)
   operations (grow often), each a visitor:
        EvalVisitor      visitNumberLit  visitBinaryOp  visitFunctionCall
        PrintVisitor     "                                             "
        TypeCheckVisitor "                                             "
   add an operation → new visitor class. node classes never change.
🧠
Compilers and linters run on Visitor: Babel, ESLint, TypeScript, and Roslyn traverse the AST with visitors — one visitor per pass (lint rule, transform, type-check). The node types are fixed; the passes multiply.
🩺
A tax auditor visiting different account types: the accounts (checking, savings, brokerage) are stable; the auditor (visitor) knows how to process each. Next year a new audit (visitor) arrives without changing the accounts.
Visitors add operations without touching node classes
interface Visitor { number(n: NumberLit): any; binary(b: BinaryOp): any }
interface Node { accept(v: Visitor): any }

class NumberLit implements Node { constructor(readonly value: number){}
  accept(v: Visitor){ return v.number(this) } }             // double dispatch
class BinaryOp implements Node { constructor(readonly op: string, readonly l: Node, readonly r: Node){}
  accept(v: Visitor){ return v.binary(this) } }

class EvalVisitor implements Visitor {                       // one operation = one visitor
  number(n){ return n.value }
  binary(b){ const l=b.l.accept(this), r=b.r.accept(this); return b.op==='+'? l+r : l*r }
}
// add PrintVisitor / TypeCheckVisitor later — NumberLit/BinaryOp never change
🧒
In plain wordsImagine a fixed set of shapes, and you keep inventing new things to do to them (measure them, paint them, count them). Instead of teaching every shape every new trick, you make a "visitor" for each trick that knows how to handle each shape. Want a new trick? Write a new visitor. The shapes never change — which is perfect when the shapes are settled but the list of things-to-do keeps growing.
🌍
In the wildCompilers & linters (Babel, ESLint, TypeScript, Roslyn, LLVM passes) traversing ASTs, document/DOM tree processing, serialization visitors, query-plan walkers in databases, and IR optimization passes. It's the go-to when you have a fixed node hierarchy and a growing set of operations over it.

✅ Do

  • Use it when the type set is stable but operations grow (ASTs, document trees)
  • Keep each operation cohesive in one visitor
  • Use it to run many passes over the same structure

❌ Don't

  • Use it when you frequently add new element types (every visitor must then change)
  • Reach for it in languages with pattern matching / sum types — a match is simpler
Gotcha: Visitor makes a hard tradeoff: adding an operation is cheap (one new visitor), but adding an element type is expensive (you must add a method to every visitor). So it's right only when the type hierarchy is stable and operations churn — the exact opposite situation wants operations-as-methods-on-types instead. This is the "expression problem." Also, Visitor is the most boilerplate-heavy GoF pattern (double dispatch, a method per type); in languages with pattern matching / algebraic data types (Rust, Scala, Kotlin, TS discriminated unions), a switch/match on node type is simpler and does the same job — reserve classic Visitor for OO languages lacking that.

25Repository — a collection-like API over storage★ backbone▶

Scenario: your business logic needs to load and save Orders, but you don't want SQL (or Mongo queries, or HTTP calls) smeared through it. A Repository gives your domain a collection-like interface — orders.byId(id), orders.save(order) — and hides whether that's Postgres, an API, or an in-memory list (crucial for tests).

What

Repository: mediate between the domain and data-mapping layers with a collection-like interface for accessing domain objects, hiding the persistence mechanism.

Why

It keeps persistence details out of business logic, centralizes queries, and lets you swap the real database for an in-memory fake in tests (Dependency Inversion, OOP topic 17).

How

Define a repository interface in the domain (save, byId, findBy…); implement it per datastore in the infrastructure layer; inject it into services.

Domain talks to a collection, not to SQL
   OrderService ──► «OrderRepository { byId  save  findOpenFor(customer) }»
                             ▲                         ▲
                    PostgresOrderRepo          InMemoryOrderRepo (tests)
   business logic never writes SQL; swap the implementation without touching it
🧠
It combines Facade + Adapter + DIP: a simple collection facade over your data store, adapting the DB's API to your domain's language, with the interface owned by the domain so you can inject a fake. Spring Data and Rails/Django's ORM layers institutionalize it.
🗂️
Like an in-memory list you can query: orders.findOpenFor(customer) reads like operating on a collection — you don't think about tables, joins, or connection pools; the repository handles the mapping.
Domain-owned interface, swappable implementations
interface OrderRepository {                         // defined in the DOMAIN
  byId(id: string): Promise<Order | null>
  save(order: Order): Promise<void>
  findOpenFor(customerId: string): Promise<Order[]>
}
class PostgresOrderRepo implements OrderRepository { /* SQL + row↔Order mapping */ }
class InMemoryOrderRepo implements OrderRepository {   // for fast, DB-free tests
  private store = new Map<string, Order>()
  async byId(id){ return this.store.get(id) ?? null }
  async save(o){ this.store.set(o.id, o) }
  async findOpenFor(c){ return [...this.store.values()].filter(o => o.customerId===c && o.isOpen()) }
}
// OrderService(new PostgresOrderRepo()) in prod;  OrderService(new InMemoryOrderRepo()) in tests
🧒
In plain wordsYour main code shouldn't be full of database commands. A repository is like a librarian: you say "get me order #42" or "save this order," and the librarian deals with the shelves (the database) for you. Your code just asks in plain terms. And for testing, you can swap the real library for a tiny pretend one — same requests, no real database needed.
🌍
In the wildSpring Data repositories, Rails/Django ORM layers, .NET EF Core + repository, DDD aggregates loaded/saved via repositories, and the standard "swap Postgres for an in-memory repo in unit tests" pattern. It underpins hexagonal/clean architecture (the repository is a "port"). See the N+1 and DR case studies for how repository queries meet real database behavior.

✅ Do

  • Define the repository interface in the domain; implement per datastore
  • Keep query logic in the repository, not scattered in services
  • Provide an in-memory implementation for fast tests

❌ Don't

  • Leak the ORM's query builder / SQL types through the interface
  • Add a repository over a trivial CRUD app where the ORM already suffices
Gotcha: two real-world traps. First, a leaky repository that returns the ORM's query builder or exposes IQueryable/lazy relations pushes persistence concerns right back into your domain — and reintroduces the N+1 problem when callers trigger lazy loads (Proxy, topic 11). Keep the interface in your terms, returning fully-loaded domain objects. Second, over a simple CRUD app the ORM's own models are often already a repository-ish abstraction — wrapping them in another layer is ceremony (see anti-patterns, topic 28). Add the pattern when you have real domain logic to protect from persistence detail, not reflexively.
26Pub/Sub & the event bus — decouple across services▶

Scenario: when an order is placed, billing, shipping, analytics, and email must all react — and you want to add reactions later without redeploying the order service. Publish/Subscribe broadcasts an OrderPlaced event to a broker; any number of independent services subscribe. It's Observer (topic 16) scaled across processes and machines.

What

Pub/Sub: publishers emit events to a broker/topic without knowing who consumes them; subscribers register interest and receive events independently. An event bus is the in-app version.

Why

It fully decouples producers from consumers (in time and space): add/remove/scale consumers without touching producers, absorb load spikes via the broker, and enable event-driven architectures.

How

Publish events to a topic on a broker (Kafka, RabbitMQ, Redis, SNS/SQS); consumers subscribe and process asynchronously, each at its own pace, with the broker handling delivery/retries.

Broadcast to a broker; consumers are independent
   OrderService ──publish(OrderPlaced)──► [ topic on broker ]
                                              ├─► Billing consumer
                                              ├─► Shipping consumer
                                              ├─► Analytics consumer
                                              └─► Email consumer
   producer doesn't know consumers exist. add one → subscribe, no producer change.
🧠
Kafka / RabbitMQ / SNS+SQS are pub/sub at scale: the order service just emits an event; a dozen teams' services consume it independently, replay it, and scale separately. It's the foundation of event-driven microservices (see the Event-Driven playbook).
📻
A radio broadcast: the station transmits; any number of radios tune in, and the station neither knows nor cares who's listening. New listeners need no change at the station — they just tune to the frequency (topic).
Publish an event; independent consumers react
// producer — knows only the broker + topic, not the consumers
await broker.publish('order.placed', { orderId: order.id, total: order.total().cents })

// each consumer subscribes independently, processes asynchronously, at its own pace
broker.subscribe('order.placed', async (evt) => { await billing.invoice(evt.orderId) })
broker.subscribe('order.placed', async (evt) => { await shipping.schedule(evt.orderId) })
broker.subscribe('order.placed', async (evt) => { analytics.track('order', evt) })
// add a fraud-check consumer later → just subscribe. producer never changes.
🧒
In plain wordsWhen something important happens, instead of the order service personally phoning every other service, it just announces it once to a central board ("an order was placed!"). Any service that cares is watching the board and handles its own part — billing, shipping, email. You can add a new service that watches the board anytime, and the order service never has to know or change. It's the "shout it out" idea from Observer, but across many separate programs.
🌍
In the wildKafka, RabbitMQ, Redis Pub/Sub, AWS SNS+SQS, Google Pub/Sub, NATS, and cloud event buses (EventBridge) — the backbone of event-driven microservices, domain events, CQRS/event sourcing, and the outbox pattern. In-process event buses (Node EventEmitter, Spring events, MediatR notifications) are the same shape without the network. Covered in depth in the Event-Driven Architecture playbook.

✅ Do

  • Use it to decouple producers from many independent, scalable consumers
  • Make consumers idempotent (brokers deliver at-least-once → duplicates happen)
  • Plan for dead-letter queues and retries for poison messages

❌ Don't

  • Assume exactly-once delivery or global ordering (usually you get neither for free)
  • Use async events where you need a synchronous, immediately-consistent answer
Gotcha: Pub/Sub trades tight coupling for distributed-systems hard problems. Most brokers give at-least-once delivery, so the same event can arrive twice — consumers must be idempotent or you'll double-charge a card. Ordering is often only per-partition, not global. Failures need dead-letter queues and retry policies (topic 27), and debugging becomes tracing an event across services rather than reading one stack. And it's eventually consistent: don't use it when the caller needs an immediate, consistent result. Distinguish it from in-process Observer (topic 16) — the moment a broker and the network are involved, these concerns are yours to handle. (See the Event-Driven and Distributed Systems playbooks.)
27Circuit Breaker & Retry — resilience against failure★ production▶

Scenario: a downstream service you call gets slow/unhealthy. Naïve retries pile on and make it worse; every request hangs on a timeout, threads exhaust, and the failure cascades until your whole app is down. A Circuit Breaker detects the failures and "trips" — failing fast for a while instead of hammering a dying dependency — while Retry with backoff handles transient blips.

What

Circuit Breaker: wrap a risky call so that after N failures it "opens" and fails fast (skipping the call) for a cooldown, then "half-opens" to test recovery. Retry: re-attempt transient failures, ideally with exponential backoff + jitter.

Why

They stop one slow/broken dependency from cascading into a total outage: fail fast to shed load, give the dependency room to recover, and smooth over momentary glitches.

How

Track failures; on threshold, open the circuit (return an error/fallback immediately); after a timeout, half-open and probe. Combine with bounded retries, timeouts, and bulkheads.

Closed → Open → Half-open state machine
          failures ≥ threshold
   CLOSED ──────────────────► OPEN ── fail fast (return fallback), skip the call
     ▲  (calls flow through)    │ after cooldown
     │  success                 ▼
     └──────────────────── HALF-OPEN ── let ONE probe through:
                                          success → CLOSED, failure → OPEN
   retry (bounded, exp. backoff + jitter) handles TRANSIENT blips underneath
🧠
It's an electrical circuit breaker: when current surges, it trips to protect the house instead of letting wires melt. Netflix's Hystrix, resilience4j (Java), and Polly (.NET) popularized it for microservices — trip on a failing dependency to protect the caller.
🔁
Retry with backoff + jitter is how clients survive transient errors (a brief network blip, a 503): wait 1s, 2s, 4s… with randomness so a thousand clients don't retry in lockstep and create a "thundering herd" that re-downs the service.
A minimal circuit breaker wrapping a call
class CircuitBreaker {
  private failures = 0; private openUntil = 0
  constructor(private threshold = 5, private cooldownMs = 30000) {}
  async call<T>(fn: () => Promise<T>, fallback: () => T): Promise<T> {
    if (Date.now() < this.openUntil) return fallback()          // OPEN → fail fast
    try {
      const r = await fn(); this.failures = 0; return r          // success → reset
    } catch (e) {
      if (++this.failures >= this.threshold)
        this.openUntil = Date.now() + this.cooldownMs            // trip OPEN
      return fallback()
    }
  }
}
// often composed as a Decorator (topic 9): breaker(retry(timeout(httpClient)))
🧒
In plain wordsIf something you rely on keeps failing, don't keep desperately calling it — that just makes things worse and freezes you up too. A circuit breaker notices the trouble and stops calling for a bit, so you fail quickly (maybe with a backup answer) and give the sick service time to recover. Retries handle the little hiccups by trying again after a short, growing wait. Together they keep one broken piece from dragging the whole system down.
🌍
In the wildNetflix Hystrix, resilience4j, Polly (.NET), Istio/Envoy circuit breaking, AWS SDK adaptive retries, gRPC retry policies, and service meshes. Paired with timeouts, bulkheads (isolate resource pools), and rate limiting as the standard resilience toolkit. Frequently implemented as stacked Decorators (topic 9) around a client. Core to the Distributed Systems playbook's resilience chapter.

✅ Do

  • Add timeouts + bounded retries with exponential backoff and jitter
  • Trip a circuit breaker on a failing dependency and serve a fallback
  • Only retry idempotent/safe operations

❌ Don't

  • Retry without backoff/jitter (you create a thundering-herd retry storm)
  • Retry non-idempotent calls (a "failed" charge may have succeeded → double charge)
Gotcha: retries are dangerous on non-idempotent operations — a payment that timed out may actually have succeeded, so a blind retry double-charges. Use idempotency keys, or only retry safe reads. And retries without exponential backoff + jitter cause retry storms: when a service wobbles, synchronized client retries pile on and finish it off (the "thundering herd"). Tune breaker thresholds carefully too — too sensitive and you trip on normal blips; too lax and you never protect the caller. Resilience patterns are essential in production but must be configured with these failure modes in mind, not just switched on. (See the Distributed Systems playbook.)
28Anti-patterns — patterns misused, and pattern fever★ judgment▶

Scenario: a codebase where everything is a *Manager or *Factory, there are five layers of interfaces with one implementation each, a 3,000-line ApplicationService God object, and Singletons everywhere. Every pattern was applied — and the result is harder to change than plain code. Knowing the patterns includes knowing how they go wrong.

What

Anti-patterns are common "solutions" that look reasonable but backfire — including overusing the very patterns in this playbook. The senior skill is restraint and fit.

Why

Patterns are tools with costs (indirection, ceremony, cognitive load). Applied where their problem doesn't exist, they add complexity without benefit — the opposite of their purpose.

How

Reach for a pattern only when you have evidence of its problem (repetition, real variation, a genuine boundary). Prefer the simplest thing that works; refactor toward a pattern when the need appears.

The usual suspects
   God Object / Blob   one class does everything; every change touches it
   Singleton abuse     global mutable state disguised as a pattern (topic 5)
   Pattern fever /      forcing Factory/Visitor/Strategy where a function/if/enum
     "Golden Hammer"    would do — complexity for its own sake
   Premature abstraction  interfaces & layers for variation that never comes (YAGNI)
   Spaghetti (no structure)  ↔  Lasagna (too many thin indirection layers)
   Poltergeist          classes that just pass calls through, adding nothing
🧠
The "Golden Hammer": "when all you have is a hammer, everything looks like a nail." A dev who just learned Visitor visitors everything; a team that discovered microservices splits a CRUD app into 30 of them. The tool isn't wrong — the reflexive over-application is.
⚖️
Two ditches on one road: spaghetti (no patterns, everything tangled) and lasagna (so many abstraction layers you can't find the actual logic). Good design steers between under- and over-engineering — the same calibration point as OOP's "when NOT to use OOP."
Over-patterned vs simple-and-correct
// ❌ pattern fever: a Strategy + Factory + Singleton to add two numbers
const adder = AdderStrategyFactory.getInstance().create('sum')
adder.execute(a, b)

// ✅ it's a function.
const sum = (a: number, b: number) => a + b

// ❌ premature abstraction: 1 interface, 1 impl, no test double, no 2nd impl in sight
interface IUserNameFormatter { format(u: User): string }
class UserNameFormatterImpl implements IUserNameFormatter { /* ... */ }
// ✅ just a function until a real second case or a test seam actually appears
const formatName = (u: User) => `${u.first} ${u.last}`
🧒
In plain wordsPatterns are power tools — great for the right job, silly for the wrong one. Using fancy patterns everywhere makes code more confusing, not less: a giant class that does everything, "managers" wrapping "managers," or a whole factory just to add two numbers. The pro move is using the simplest thing that works, and only reaching for a pattern once you actually hit the problem it solves. Knowing a pattern includes knowing when not to use it.
🌍
In the wildEnterprise Java's AbstractSingletonProxyFactoryBean became a meme for over-abstraction; "FizzBuzz Enterprise Edition" satirizes pattern fever; "distributed monolith" is microservices misapplied; and countless codebases carry God *Service/*Manager classes and interface-per-class layers no one needed. The reaction — Go's simplicity ethos, "YAGNI," "rule of three" before abstracting — is the industry course-correcting against pattern overuse.

✅ Do

  • Start simple; refactor toward a pattern when the problem actually appears
  • Apply the "rule of three" — abstract after the third real repetition, not the first
  • Split God objects; delete pass-through layers that add nothing

❌ Don't

  • Add a pattern to show you know it, or "in case we need it later" (YAGNI)
  • Wrap every class in an interface it will never have a second implementation of
  • Let one class or one mediator/facade become the God object again
Gotcha: the deepest lesson of this whole playbook — patterns are a means, not a scorecard. The goal was always code that's easy to understand and change safely; a pattern that doesn't serve that goal is just cost. Over-engineering (needless abstraction, premature patterns) is as real a failure as under-engineering (spaghetti, God objects), and it's the more seductive one because it looks sophisticated. Calibrate to the actual problem: know all 28 of these so you can recognize and name them — and have the judgment to reach for one only when its problem genuinely shows up. Simplicity is the default; patterns earn their place.
